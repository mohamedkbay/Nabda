Build with Nabda

A practical reference for installing the local stack, testing safely in Mock mode, and integrating the versioned transactional messaging API.

Get started

Overview

Nabda is a multi-tenant API for expected transactional messages. An organization authenticates with its own API key, creates a message, and reads the result while background workers coordinate queueing, provider dispatch, status checks, and signed webhook deliveries.

Base URLs and environments

EnvironmentBase URLDelivery
Local simulationhttp://localhost:3000mock · no SMS
Same-LAN gatewayhttp://<private-ip>:3000Android SIM gateway with explicit live confirmation

All business endpoints use the /v1 prefix. Health endpoints are unversioned because they describe the running service rather than a tenant resource.

Mock is the default and required development provider. It runs the real validation, database, queue, usage, status, and webhook paths without sending a real SMS or calling an SMS provider.

Windows Controller

This is the simplest one-computer setup. Install the x64 program, leave it running in the system tray, and manage messages, contacts, opt-outs, campaigns, and the Android phone from the browser dashboard. It uses local SQLite and needs no Docker services.

  1. Install Nabda-Controller-0.1.0-Setup-x64.exe and open Nabda from the Start menu.
  2. The tray opens a protected browser session at http://127.0.0.1:3210. Closing the browser does not stop the controller.
  3. Open Device, create a two-minute QR, then tap Scan controller QR in Nabda Agent. The code works once and does not expose the permanent device key.
  4. Tap Start connection on Android. Type ENABLE_LIVE_SMS in Windows only when carrier sending is intended, then complete the separate Android confirmation.
  5. Add one contact or import CSV, TXT, or VCF. The importer supports Name,Emails,PhoneNumbers and semicolon-separated numbers.
  6. Optionally enable Start with Windows from the tray menu.
Private network only. Allow TCP 3210 in Windows Defender Firewall only for the Private profile. Never port-forward it or expose it through a public tunnel.

Installation

Docker Compose starts PostgreSQL, Redis, migrations, the API, and the worker. The default profile is a safe Mock simulation; the separate LAN profile enables the Android SIM gateway only after explicit server and device confirmations.

1. Prepare secrets

Shell
cp .env.example .env
chmod 600 .env
openssl rand -hex 24      # POSTGRES_PASSWORD
openssl rand -base64 48  # API_KEY_HASH_SECRET
openssl rand -base64 32  # APP_ENCRYPTION_KEY

Place three different generated values in .env. APP_ENCRYPTION_KEY must decode to exactly 32 bytes. Keep the file owner-only with chmod 600 and never commit it.

2. Start and migrate

Docker Compose
docker compose up --build -d
docker compose ps -a
docker compose logs --tail=100 api worker migrate

3. Provision the permanent Free plan

Docker Compose · Free plan
docker compose run --rm migrate npm run db:free

The command prints a test API key once and creates a permanent Free workspace with 5,000 accepted operations per month and a ten-per-minute limit. Running it again rotates the local key without resetting usage in the same month.

With PostgreSQL and Redis already running, Node.js 22 or newer can run the API and worker directly.

Terminal 1 / Terminal 2
npm install
npm run db:migrate
npm run db:free
npm run dev

# In a second terminal
npm run worker:dev

Authentication

Protected endpoints accept the raw organization key as a Bearer credential. The x-api-key header is also supported for server clients, but Authorization is preferred. Do not send conflicting values in both headers.

AUTHAuthorization: Bearer nbda_test_…
API keys are server credentials. Never place them in browser JavaScript, mobile bundles, URLs, screenshots, source control, or request logs. The database stores only an HMAC hash.

Phone agent

Connect the phone on the same Wi-Fi

The native Android agent stays in a foreground service, claims one queued item at a time, sends it through the company SIM, reports the result, and immediately asks for the next item. It never downloads the entire campaign.

1. Start the explicit LAN mode

Docker Compose · LAN live
docker compose -f docker-compose.yml -f docker-compose.live.yml up --build -d
docker compose -f docker-compose.yml -f docker-compose.live.yml run --rm migrate npm run db:free
docker compose -f docker-compose.yml -f docker-compose.live.yml run --rm migrate npm run db:device-agent

The last two commands print the live API key and device token once. Keep the API key in your server application and paste only the device token into the phone.

2. Install the small LAN APK

USB · one phone
export ANDROID_SDK_ROOT=/Users/mohamedbay/.android-sdk
npm run android:install:lan

The installer verifies the APK checksum and confirms that this deliberate build contains the Android SMS permission before installing it.

3. Enter two values and connect

  1. Enter http://<computer-private-ip>:3000, for example http://192.168.1.20:3000.
  2. Paste the one-time nbda_device_… token.
  3. Confirm expected-message use, tap Connect & start, and approve the Android SMS permission.
Use a trusted private network. The internal LAN build permits HTTP only to RFC1918 private addresses. PostgreSQL and Redis stay bound to the computer. Public deployments require HTTPS.

Device token authentication

The phone protocol uses a device token scoped to exactly one organization and one device. It is a separate credential from the organization API key.

CredentialWhere it belongsWhat it can call
API keyYour trusted server application/v1/messages, /v1/usage, /v1/contacts, and other tenant endpoints
Device tokenNabda Agent on one phone/v1/device/* only
AUTHAuthorization: Bearer <device_token>

Every device request uses the header above. The server stores a domain-separated HMAC hash, while the app encrypts the token with Android Keystore. A missing, revoked, rotated, or wrong token returns 401 invalid_device_token.

Never paste an organization API key into the phone app. If a device token may have been exposed, provision a replacement; provisioning rotates the active local token for that device.

Device pull protocol

The agent follows a fenced four-call sequence. Claim only reserves work; begin is the final server safety check. An event is accepted only for the same device, message, lease, stable attempt, and server-bound execution mode. A simulation credential cannot switch itself to live through request data.

1. Report availability

POST/v1/device/heartbeat

Sends the app version, Android version, optional battery/network telemetry, and the credential-bound mode. The response includes server time, device ID, a two-second idle poll delay, and whether live reporting is enabled.

2. Reserve one message

POST/v1/device/messages/claim

Sends limit: 1 and the credential-bound mode. An empty queue returns messages: []. A reservation returns one message plus a short-lived lease token. Reserving alone never authorizes an SMS.

3. Begin the stable attempt

POST/v1/device/messages/{id}/begin

Returns the claim lease with a stable attempt_id. The server rechecks expiry, opt-out state, ownership, subscription state, and device spacing before authorizing dispatch. Repeating the identical begin is idempotent.

4. Record the result

POST/v1/device/messages/{id}/events

Reports the same lease and attempt with a unique event_id. An identical replay is safe; a mutated replay conflicts. Simulation finishes as cancelled/simulation_only. Live transport reports sent or failed; an uncertain restart enters manual review and is never retried blindly.

ResponseAgent action
401 invalid_device_tokenStop and replace the device token; do not retry the same credential.
409 or 410 lease errorDo not dispatch; discard the rejected reservation and wait for the next safe poll.
429 rate_limitedWait until Retry-After before beginning another attempt.
503 device_agent_disabledThe server feature is off; stop polling until the local operator enables the simulation agent.

Get a message

GET/v1/messages/:id

Returns one organization-owned message in the same public representation used by create. A missing, malformed, deleted, or different-organization ID returns message_not_found without revealing cross-tenant existence.

cURL · messages:read
curl --header "Authorization: Bearer $NABDA_API_KEY" \
  http://localhost:3000/v1/messages/MESSAGE_ID

Statuses and state flow

NEWqueued → sent → delivered

Queued and sent are non-terminal. Delivered, failed, expired, and cancelled are terminal. The exact path depends on provider results, schedule, expiry, opt-out checks, and operating failures.

StatusMeaningTerminal
queuedRecorded and waiting for scheduled background dispatchNo
sentProvider accepted dispatch; final delivery may still be unknownNo
deliveredProvider confirmed deliveryYes
failedA permanent or safely non-retriable failure occurredYes
expiredThe message passed its expiry before completionYes
cancelledCancelled before dispatch, including a late opt-out checkYes
Sent is not delivered. Build customer-facing state from delivered or another terminal outcome, not from API acceptance or provider acceptance alone.

Usage, quota, and rate limits

GET/v1/usage

Returns the current monthly period, accepted message usage, remaining quota, per-minute message limit, and contact capacity. The Free plan reports 5,000 monthly operations, 10 per minute, and up to 10,000 contacts.

200 · usage
{
  "data": {
    "plan": "free",
    "subscription_status": "active",
    "period_start": "2026-08-01T00:00:00.000Z",
    "period_end": "2026-09-01T00:00:00.000Z",
    "messages_used": 1,
    "message_limit": 5000,
    "messages_remaining": 4999,
    "per_minute_rate_limit": 10,
    "max_contacts": 10000
  }
}

New accepted operations increment usage. An exact idempotent replay does not consume another credit. Quota and per-minute failures return 429; respect Retry-After and avoid tight retry loops.

Queue

GET/v1/queue

Returns a current summary for the authenticated organization. It is an operating signal, not a list of message content.

FieldMeaning
queued_totalAll messages currently in queued status
readyPending dispatch whose schedule is due
scheduledPending dispatch scheduled for the future
processingJobs currently claimed by a worker
oldest_queued_atTimestamp of the oldest queued message, or null
A growing ready count or old oldest_queued_at needs attention. Check worker health, Redis, PostgreSQL, device availability, subscription status, and rate controls before retrying client requests.

Contacts

Contacts store an organization’s normalized recipient record. Creation requires an active subscription and is capped by max_contacts; updating an existing active phone remains atomic at the limit.

Create or update

POST/v1/contacts
cURL · contacts:write
curl --request POST http://localhost:3000/v1/contacts \
  --header "Authorization: Bearer $NABDA_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "name": "Sample Customer",
    "phone": "+218910000000",
    "consent_reference": "account-842",
    "tags": ["customer", "orders"],
    "metadata": {"customer_id": "842"}
  }'

The name is 1–120 characters. phone must normalize to E.164. Up to 50 unique tags are allowed, each 1–64 characters. metadata is an object up to 4096 serialized bytes. A new contact returns 201; an update returns 200.

List with cursor pagination

GET/v1/contacts?limit=20&cursor=…

limit defaults to 20 and accepts 1–100. Use meta.next_cursor exactly as returned; do not construct or modify it. A null cursor means there is no next page.

Delete contact data

DELETE/v1/contacts/:id

Returns 204 and removes the contact row while preserving only the deletion fact in the audit log. A contact is not an opt-out: use the opt-out endpoint for a recipient stop request.

Opt-outs

POST/v1/opt-outs

Adds the normalized phone to the authenticated organization’s active blocklist. The operation is idempotent for an already-active number and cancels queued messages for that recipient inside the same organization.

cURL · opt_outs:write
curl --request POST http://localhost:3000/v1/opt-outs \
  --header "Authorization: Bearer $NABDA_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "phone": "+218910000000",
    "reason": "Recipient requested a stop"
  }'
The blocklist is checked twice. Nabda checks before accepting a new request and again in the worker before dispatch, so a late stop request can cancel a queued message.

Webhooks and HMAC signatures

Active webhooks receive organization message events. In this MVP, webhook records and encrypted secrets are provisioned administratively; there is no public API endpoint for creating or rotating webhooks yet.

Delivery headers

HeaderMeaning
x-nabda-delivery-idUnique delivery attempt record
x-nabda-event-idStable event identifier for deduplication
x-nabda-eventEvent type such as message.delivered
x-nabda-timestampUnix seconds used in the signature input
x-nabda-signaturev1=<hex HMAC-SHA256>

Signature input

The signed byte string is timestamp + "." + rawBody. Compute HMAC-SHA256 with the endpoint secret and compare the hex digest after the v1= prefix using constant-time comparison.

Node.js · exact Nabda v1 signature
import { createHmac, timingSafeEqual } from "node:crypto";

export function verifyNabdaWebhook(rawBody, headers, secret) {
  const timestamp = headers["x-nabda-timestamp"];
  const provided = headers["x-nabda-signature"];
  if (!Buffer.isBuffer(rawBody)) return false;
  if (!/^\d{10,}$/.test(timestamp ?? "")) return false;
  const signedAt = Number(timestamp);
  const now = Math.floor(Date.now() / 1000);
  if (!Number.isSafeInteger(signedAt) || Math.abs(now - signedAt) > 300) {
    return false;
  }
  if (!timestamp || !provided?.startsWith("v1=")) return false;

  const expectedHex = createHmac("sha256", secret)
    .update(Buffer.from(`${timestamp}.`, "utf8"))
    .update(rawBody)
    .digest("hex");
  const providedHex = provided.slice(3);
  if (!/^[a-f0-9]{64}$/i.test(providedHex)) return false;

  const expected = Buffer.from(expectedHex, "hex");
  const actual = Buffer.from(providedHex, "hex");
  return expected.length === actual.length &&
    timingSafeEqual(expected, actual);
}
Verify the raw body before parsing. Re-serializing JSON can change whitespace or key order and invalidate a correct signature. Also reject stale timestamps according to your replay window.

Webhook delivery and retries

Nabda treats any 2xx response as success. Network errors, timeouts, and non-2xx responses are recorded as failed attempts and may be retried until the configured delivery reaches its maximum attempt count.

  • Require HTTPS outside tests.
  • Verify HMAC and store the event ID under a unique constraint.
  • Persist the event, return 2xx quickly, and move slow work to your queue.
  • Return success for an already-processed event without repeating side effects.
  • Log delivery and event IDs, but not secrets or full sensitive payloads.

The worker validates public destinations and blocks private, loopback, link-local, and reserved network addresses to reduce server-side request forgery risk.

Troubleshooting

The readiness endpoint returns 503

Run docker compose ps -a and inspect API, migrate, PostgreSQL, and Redis logs. Confirm DATABASE_URL and REDIS_URL, wait for migrations, and do not repeatedly recreate volumes.

A message stays queued

Check that the worker is running, Redis is healthy, the schedule is due, the subscription and device are active, and the queue ready/processing counts are moving. The Mock worker must still run; the API alone does not dispatch.

The API key returns 401

Use the complete raw key printed by db:free, remove quotes or whitespace added by copy/paste, confirm the environment uses the same API_KEY_HASH_SECRET as provisioning, and ensure the key is not revoked.

Idempotency returns 409

That key already represents a different body. Retry the original operation with its original body, or generate a new 16–128 character key for a genuinely new operation.

A webhook signature fails

Verify that you use the endpoint’s decrypted secret, the x-nabda-timestamp value, and the exact raw body. Strip only the v1= prefix from the provided signature and compare decoded bytes in constant time.

Usage reached the monthly limit

The Free plan renews each calendar month and does not expire. Inspect GET /v1/usage, wait for the next period, and do not create duplicate organizations to bypass fair-use limits.

Security and operating rules

The API is only one part of a safe message operation. Apply these boundaries in your application, infrastructure, and business process.

Protect secrets

Keep API keys, encryption keys, database credentials, provider credentials, and webhook secrets in protected server environments. Rotate on suspected exposure.

Minimize recipient data

Store only needed metadata, avoid message content in logs, use plan retention redaction, and preserve audit facts without retaining sensitive text forever.

Honor recipient controls

Record consent context, send expected transactional content, process stop requests promptly, and never bypass the organization blocklist.

Before any live provider

  • Complete Mock tests and confirm PROVIDER_MODE=mock and ENABLE_LIVE_SMS=false during development.
  • Use a company-owned or company-controlled Android phone and SIM.
  • Review carrier charges, fair-use policy, throughput, destination rules, and applicable law.
  • Define production quotas, rate limits, retention, monitoring, incident response, and access ownership.
  • Enable a live adapter only through an explicit production change with server-side credentials.
No unlimited or unsolicited sending. Nabda enforces platform quota and rate controls, but those do not replace carrier limits, recipient expectations, or applicable rules.
