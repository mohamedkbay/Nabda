LOCAL DESKTOP GUIDE

httpSMS Desktop

A practical guide for the independent, unofficial desktop client. The official provider documentation remains the source of truth for account, Android application, API, and carrier behavior.

Overview

Desktop stores customers, contacts, opt-outs, campaigns, queue state, message history, settings, and backups in local SQLite. The Electron main process connects to https://api.httpsms.com/v1; the renderer has no network or Node.js access.

No custom phone software. This project does not publish an APK, create a device token, run LAN pairing, or open an inbound phone endpoint.

Installation

For users

  1. Download the Windows installer from the private build artifact.
  2. Run the NSIS setup and choose an installation folder.
  3. Open httpSMS Desktop (Unofficial).
  4. Your data is created under the operating system user-data directory and remains after uninstall unless you remove it deliberately.

For developers

Local development
npm ci · npm run test:desktop · npm run dev:desktop

Node.js 24 LTS is recommended. Desktop does not require Docker, PostgreSQL, Redis, Java, Gradle, or Android SDK tools.

Provider and phone setup

  1. Create or sign in to a httpSMS account.
  2. Install the official Android application using the provider getting-started guide.
  3. Complete sign-in and SMS permissions in the official app.
  4. Copy the full Account API Key from provider settings. A phone-only key is not sufficient for Desktop.
  5. Open Integration and enter the Account API Key plus the registered From number in E.164 format.
  6. Save, then choose Test Connection.
Credential boundary. The Account API Key is encrypted with Electron safeStorage in the main process. It is excluded from SQLite, renderer storage, backups, and logs.

Testing without sending SMS

Test Connection performs only GET /v1/users/me. Unit tests inject a fake network implementation and never contact the provider. Neither path calls /messages/send.

Adding a real message to the queue after valid credentials are saved is different: the worker can submit it to the provider and may cause the official Android application to send a carrier SMS.

Contacts and opt-outs

Add only recipients who expect your messages. Each campaign recipient needs a consent reference. The local blocklist is checked before queue creation and again immediately before provider submission, so a late stop request can cancel queued work.

Messages

A message requires E.164 To, content, confirmation that the message is expected, and optional send_at, request_id, and encrypted values. Scheduling is limited to 20 days. Encryption requires a matching key in the official phone app.

Local stateMeaning
queuedWaiting for local submission
sentAccepted or reported sent by the provider
deliveredProvider delivery confirmation
failedRejected, failed, or ambiguous and awaiting manual review
expiredExpired before completion
cancelledCancelled before submission, including opt-out
Duplicate protection. A network failure after a send may leave the outcome unknown. Desktop marks the message for manual review and does not retry blindly.

Campaigns and pacing

Campaigns use saved contacts, skip local opt-outs, require consent confirmation, and pace provider submissions from 1 to 10 messages per minute. Campaign size is capped at 500 recipients in the UI. Provider and carrier limits still apply independently.

Status polling

Desktop reads status with GET /v1/messages/:id. The polling interval is configurable from 15 seconds to 5 minutes. A temporary polling error does not rewrite the current message state.

Backups

Export creates a validated SQLite backup after a full WAL checkpoint. Import validates integrity and schema before atomic replacement. The provider key is stored separately and is never included.

Security

  • Renderer isolation, sandboxing, and Node integration disabled.
  • Strict Content Security Policy with renderer network access disabled.
  • Named IPC methods with Zod validation and exact sender checks.
  • External navigation limited to HTTPS and opened in the system browser.
  • Secrets remain in the main process and use operating-system encryption.
  • No local HTTP server, custom Android agent, QR pairing, or inbound port.
  • Opt-out checks at acceptance and immediately before dispatch.
  • No automatic retry when provider acceptance is uncertain.

Troubleshooting

Test Connection fails

Confirm internet access, use the full Account API Key from provider settings, and verify the provider service is reachable. The test sends no SMS.

A message stays queued

Confirm Integration has both a key and a valid From number. Check the schedule and local opt-out state.

A message requires manual review

The provider outcome was ambiguous. Check the provider dashboard or refresh status before creating another message.

The official Android app is offline

Follow the provider's Android permissions, battery, connectivity, and registered-number guidance. Desktop does not control the phone connection.

Webhooks

Phase one polls status and does not expose a local webhook receiver. Provider webhooks require a stable public HTTPS callback and a separate secured service using the provider's current signing guidance.
