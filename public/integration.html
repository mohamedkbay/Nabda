Message architecture

Four clear responsibilities. One observable result.

Each layer has a small job, which keeps the provider replaceable and makes failed work easier to inspect and retry.

01Your application

Authenticates with an organization key and creates an idempotent request.

02Nabda API

Validates content, quota, rate limits, recipient status, and ownership.

03Queue & worker

Claims ready jobs, records events, and delegates through the configured provider adapter.

04Company device

Uses the company-owned Android phone and SIM when live sending is deliberately enabled.

Company-owned device

The phone is part of your operational boundary.

A live setup requires a supported Android phone, an active SIM owned or controlled by the company, stable connectivity, and compliance with the mobile carrier’s rules.

Start in Mock mode

The development stack defaults to Mock. It exercises authentication, persistence, queue handling, states, and webhook deliveries without sending a real SMS.

Register device ownership

Associate every device with exactly one organization. Provider credentials remain server-side and are never returned to API clients.

Operate within carrier policy

Platform limits do not override SIM or carrier limits. Carrier pricing, fair-use rules, throughput, and local regulations may all apply.

Live SMS stays off during development. Moving from Mock to a provider is an explicit operational change, never an automatic Free-plan action.

Queue & delivery

Accept quickly. Process carefully.

The API records an accepted message before background dispatch. Workers claim ready records safely so multiple workers can scale without claiming the same job.

Ready and scheduled work

Messages can wait for immediate processing or a future schedule. The queue summary separates ready, scheduled, and processing counts.

Explicit terminal states

A message progresses through queued and sent before a terminal result: delivered, failed, expired, or cancelled.

Retention-aware cleanup

After the plan retention window, terminal message content and sensitive metadata are redacted while state, events, usage, and audit history remain.

Data boundaries

Organization context follows every record.

Keys, devices, contacts, messages, events, webhooks, opt-outs, usage, and audit entries are modeled per organization from the beginning.

API key isolation

Only a hash is stored. Scopes limit each key to the operations it needs.

Contact ownership

Phone uniqueness, pagination, deletion, and opt-out checks stay inside one organization.

Audit without permanent content

Operational history can remain after sensitive message content is redacted by policy.
