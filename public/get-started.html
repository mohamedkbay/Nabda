01

Confirm the local requirements

Use a development machine with Docker Desktop or Docker Engine and Compose. The stack starts the API, worker, PostgreSQL, and Redis together.

  • Docker and Docker Compose are available
  • Ports 3000, 5432, and 6379 are available or adjusted
  • The project .env file is created from .env.example
  • PROVIDER_MODE remains mock and ENABLE_LIVE_SMS remains false
No phone is needed for this stage. Mock mode is the required safe default for installation and integration testing.

02

Start and verify the stack

Copy the example environment, restrict it to its owner, generate three distinct local secrets, and paste them into .env before starting. Migrations run before the API becomes ready.

Shell · local installation
cp .env.example .env
chmod 600 .env
# Generate POSTGRES_PASSWORD, API_KEY_HASH_SECRET,
# and APP_ENCRYPTION_KEY, then paste each into .env:
openssl rand -hex 24
openssl rand -base64 48
openssl rand -base64 32

docker compose up --build -d
docker compose ps
curl http://localhost:3000/health/ready

A ready response confirms that the API can reach its required services. If it fails, inspect the troubleshooting section before proceeding.

03

Provision a Free organization and keep its key secret

Run the local Free-plan provisioner. It creates a permanent workspace with a monthly allowance of 1,000 accepted operations and prints a test API key. Copy the key into your shell for the current session; never commit it to Git.

Shell · permanent Free plan
docker compose run --rm migrate npm run db:free
export NABDA_API_KEY='paste-the-printed-local-key'
The raw key is shown only when created. The database stores a secure hash. If the raw value is lost, create a replacement rather than trying to recover it.

04

Create the first Mock message

Use a realistic E.164 test destination but never a real person’s number in local fixtures. Give the intended operation a stable idempotency key.

cURL · POST /v1/messages
curl -X POST http://localhost:3000/v1/messages \
  -H "Authorization: Bearer $NABDA_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: getting-started-001" \
  -d '{
	    "to": "+218910000000",
	    "content": "Your verification code is 123456.",
	    "purpose": "authentication",
	    "consent_confirmed": true,
	    "consent_reference": "local-test-001"
  }'

Save the returned message ID. A 202 response means the operation was accepted and queued. Because the provider is Mock, it does not send an SMS.

05

Read status, usage, and queue

Use the message ID from the accepted response. The worker should move the Mock message through the configured state path. Usage and queue endpoints expose the organization’s current operating envelope.

Shell · replace MESSAGE_ID
curl -H "Authorization: Bearer $NABDA_API_KEY" \
  http://localhost:3000/v1/messages/MESSAGE_ID

curl -H "Authorization: Bearer $NABDA_API_KEY" \
  http://localhost:3000/v1/usage

curl -H "Authorization: Bearer $NABDA_API_KEY" \
  http://localhost:3000/v1/queue

Next, configure a local webhook receiver, keep its secret outside source control, and verify HMAC before processing events.

06

Prepare for a company device deliberately

Completing local Mock tests does not automatically enable live sending. A production setup needs an explicit organization onboarding decision and operating review.

  • Company-owned or company-controlled Android phone and SIM
  • Recipient workflow records consent context and honors opt-outs
  • Carrier costs, fair-use rules, throughput, and local rules reviewed
  • Production secrets installed server-side only
  • Quota, rate limit, retention, monitoring, and incident ownership defined
Do not switch providers just to finish this guide. The local phase is complete when the Mock flow, security checks, and operational boundaries are understood.
