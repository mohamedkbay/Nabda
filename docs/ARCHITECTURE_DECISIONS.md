# قرارات معمارية — نبضة API SaaS

الحالة: مقبولة للمرحلة الأولى

آخر تحديث: 2026-08-30

## السياق والحدود

المنتج منصة SaaS متعددة العملاء لإرسال رسائل معاملات متوقعة ومصرح بها عبر هاتف وشريحة تملكهما كل شركة. الاشتراك يغطي استخدام المنصة ضمن حدود، ولا يمثل وعدًا بإرسال غير محدود. الأولويات هي عزل المؤسسات، منع التكرار، احترام opt-out حتى آخر لحظة ممكنة، وإمكانية استبدال المزود الخارجي لاحقًا.

المرحلة الأولى ليست منصة حملات تسويقية، ولا تحاول تجاوز حدود شركات الاتصالات أو أنظمة مكافحة الرسائل المزعجة، ولا توفر ضمان «exactly once» لا تستطيع شبكة SMS نفسها تقديمه.

## ADR-001: Modular monolith بعمليتي API وWorker

**القرار:** نستخدم TypeScript وFastify في حزمة واحدة منظمة إلى وحدات، مع تشغيل `server.ts` و`worker.ts` كعمليتين منفصلتين. PostgreSQL هو مصدر الحقيقة وRedis/BullMQ وسيط للمهام.

**السبب:** هذا أبسط من microservices للمرحلة الأولى، لكنه يفصل دورة طلب HTTP عن الاتصال البطيء بالمزود وتسليم webhooks. يمكن زيادة عدد عمليات العامل مستقلًا دون تقسيم مبكر للنظام.

**النتيجة:** يجب ألا يحتوي route على اتصال إرسال خارجي. يسجل API الرسالة وحدثها وoutbox داخل transaction، ثم ينشر dispatcher مهمة تحمل المعرّف فقط.

## ADR-002: PostgreSQL مصدر الحقيقة وRedis قابل لإعادة البناء

**القرار:** المؤسسات والاشتراكات والأجهزة والرسائل والأحداث والحصص وعمليات webhook تحفظ في PostgreSQL. Redis يستخدم للطابور ومحدد المعدل والأقفال القصيرة فقط.

**السبب:** قد يفقد Redis بيانات مؤقتة أو يعاد تشغيله؛ لا يجوز أن يؤدي ذلك إلى فقد سجل تجاري أو إعادة احتساب حصة العميل.

**النتيجة:** job payload لا يحمل أسرارًا أو سجلًا كاملًا، بل `messageId` أو `deliveryId`. يعيد العامل تحميل الحالة من PostgreSQL ويتجاهل المهمة إن كانت الحالة نهائية. outbox أو reconciler يعيد نشر الرسائل `queued` التي لم تصل إلى Redis. حجم pool مضبوط لكل عملية، وتوازي dispatch مشتق منه كي تبقى اتصالات متاحة للمصالحة وoutbox. لا يوجد limiter عالمي يعاقب كل المؤسسات؛ الفواصل الحاكمة تُحجز ذريًا في PostgreSQL لكل مؤسسة وجهاز، وتُنقل المهمة المحدودة إلى delayed بلا استهلاك محاولة.

## ADR-003: عزل المؤسسات في الاستعلام والقيود

**القرار:** كل جدول يملكه عميل يحتوي `organization_id NOT NULL`. لا يقبل API هذا المعرّف من العميل؛ يستخرجه من API key. تستخدم المستودعات `(organization_id, id)`، وتستخدم العلاقات الحساسة foreign keys مركبة تمنع ربط جهاز أو مفتاح من مؤسسة برسالة مؤسسة أخرى.

**السبب:** فلتر التطبيق وحده معرض للنسيان، وFK عادي على `id` لا يمنع cross-tenant reference عند وجود خطأ برمجي.

**النتيجة:** تعيد قراءة مورد تابع لمؤسسة أخرى `404` لتجنب كشف وجوده. PostgreSQL RLS مؤجل إلى مرحلة تتوفر فيها أدوار DB منفصلة و`SET LOCAL` منضبط؛ تفعيله جزئيًا مع مستخدم database owner يعطي إحساسًا زائفًا بالأمان.

## ADR-004: مفاتيح API عشوائية وHMAC hash

**القرار:** المفتاح الخام يحتوي public prefix وسرًا عشوائيًا 32 بايت، ويعرض مرة واحدة. يخزن النظام prefix و`HMAC-SHA256(API_KEY_HASH_SECRET, rawKey)` فقط، ويتحقق بمقارنة ثابتة الزمن.

**السبب:** prefix يتيح العثور على الصف دون تخزين السر. HMAC سريع ومناسب لسر عشوائي عالي entropy، بينما يمنع pepper الموجود خارج قاعدة البيانات الاستفادة المباشرة من dump.

**النتيجة:** يلزم دعم `hash_version` لدوران pepper مستقبلًا. تخفى ترويسات Authorization وAPI key ونصوص الرسائل من logs. إبطال المفتاح فوري ولا يتطلب تغيير مفاتيح المزود.

## ADR-005: بيانات المزود وأسرار webhooks مشفرة

**القرار:** القيم التي يحتاج الخادم استعادتها — مفتاح المزود وسر توقيع webhook — تشفر بـAES-256-GCM باستخدام `APP_ENCRYPTION_KEY` من البيئة. لا يعاد أي منها إلى عميل API.

**السبب:** hashing لا يصلح لقيمة يجب استخدامها لاحقًا، والتخزين الصريح يحول تسريب قاعدة البيانات إلى وصول مباشر للمزود.

**النتيجة:** كل ciphertext يتضمن version وIV وauthentication tag. دوران مفتاح التشفير يحتاج key version وعملية إعادة تشفير. لا يسمح للعميل بتغيير base URL للمزود، حتى لا يوجه الخادم إلى وجهة تسرق credential.

## ADR-006: Idempotency على مستوى المؤسسة

**القرار:** `Idempotency-Key` مطلوب في `POST /v1/messages`. يوجد قيد unique على `(organization_id, idempotency_key)`، وتحفظ بصمة canonical للحقول المؤثرة في الطلب.

**السبب:** إعادة HTTP بعد timeout أمر طبيعي. إنشاء رسالة ثانية قد ينتج SMS مكررة، بينما unique constraint يجعل السباقات آمنة على مستوى قاعدة البيانات.

**النتيجة:** نفس المفتاح والبصمة يعيد المورد الموجود دون حصة أو job جديد. نفس المفتاح مع بصمة مختلفة يعيد `409 idempotency_conflict`. لا تعتمد idempotency على ذاكرة العملية أو Redis.

## ADR-007: الحصة عند القبول ومحدد معدل ذري

**القرار:** تحسب رسالة جديدة على حصة فترة الاشتراك عند انتقالها إلى `queued`. يتم increment لعداد PostgreSQL داخل transaction بشرط ألا يتجاوز الخطة. يستخدم Redis script ذريًا لمعدل الدقيقة، مع fail-closed افتراضيًا.

**السبب:** `COUNT(*)` غير المقفول يسمح بتجاوز الحد تحت التزامن، والاعتماد على Redis للحصة الشهرية يفقد الدقة بعد restart.

**النتيجة:** replay والطلب المرفوض لا يحتسبان. الإلغاء أو الفشل اللاحق لا يعيدان الرصيد لأن المنصة قبلت وعالجت الطلب؛ يجب إظهار هذه الدلالة بوضوح في `GET /v1/usage`. يمكن إضافة سياسة credits لاحقًا دون تغيير سجل الرسائل.

## ADR-008: حالة عامة مستقلة عن حالات المزود

**القرار:** العقد العام يقتصر على `queued`, `sent`, `delivered`, `failed`, `expired`, `cancelled`. يحفظ raw provider status في event داخلي ولا يعرض باعتباره عقدًا ثابتًا.

**التحولات المسموحة:**

```text
queued  -> sent | failed | expired | cancelled
sent    -> delivered | failed | expired
```

**السبب:** كل مزود يملك أسماء ومعاني مختلفة. ربط API بها يجعل استبدال المزود كسرًا للعملاء.

**النتيجة:** قبول المزود لعملية dispatch يساوي `sent` حتى إن سمى حالته الداخلية `pending`. كل انتقال يكتب `message_event` append-only. الأحداث المكررة deduplicated بمعرّف المزود، والأحداث المتأخرة تحفظ حتى عندما لا تغير الحالة النهائية.

## ADR-009: BullMQ at-least-once مع idempotency لدى المزود

**القرار:** `jobId` مشتق من `message.id`، والعامل يطالب الرسالة ذريًا ويعيد فحص حالتها. يرسل adapter `request_id = message.id` إلى المزود حين يدعم ذلك.

**السبب:** قد يعيد BullMQ المهمة بعد crash. قد يحدث crash أيضًا بعد قبول المزود وقبل حفظ النتيجة.

**النتيجة:** لا نزعم exactly-once. إذا انقطع الاتصال وأصبح قبول المزود غير معلوم، تسجل الرسالة `failed` مع `failure_code=provider_outcome_unknown` ولا تعاد عميانيًا، إلا إذا كان هناك ضمان idempotency موثق أو reconciliation يؤكد عدم قبول الطلب.

تطبق المرحلة الأولى حد الدقيقة مرة ثانية عند dispatch بمفتاح المؤسسة، إلى جانب فاصل عالمي افتراضي مقداره 3 ثوانٍ. يمنع ذلك burst للرسائل المجدولة عند استئناف العامل ويحمي الخطة عبر عدة عمليات worker؛ ويمكن إضافة فاصل مستقل لكل جهاز عندما تتطلب السعة ذلك.

## ADR-010: Mock افتراضي وحاجز مزدوج للإرسال الحقيقي

**القرار:** `PROVIDER_MODE=mock` و`ENABLE_LIVE_SMS=false` هما الافتراضيان. اختيار adapter خارجي مع بقاء العلم false يفشل عند الإقلاع. بيئة test تمنع adapter الحقيقي حتى لو ضبط العلم خطأ، وDocker Compose التطويري يفرض Mock قسرًا.

**السبب:** وجود credential بالخطأ في الجهاز أو البيئة لا يجب أن يحول اختبارًا إلى إرسال فعلي.

**النتيجة:** Mock لا ينشئ أي اتصال شبكة ويعيد معرفًا وحالة deterministic قابلة للحقن في الاختبارات. تفعيل مزود فعلي عملية إنتاج مستقلة تحتاج مراجعة وبيئة أسرار، ولا توثق كخطوة تشغيل محلي.

## ADR-011: opt-out يفحص عند القبول وعند التنفيذ

**القرار:** يرفض API رقمًا موجودًا في قائمة الإيقاف، ويعيد العامل الفحص قبل أي اتصال بالمزود. يستخدم `POST /v1/opt-outs` والعامل advisory lock واحدًا على `(organization_id, phone)`؛ إضافة opt-out تلغي الرسائل `queued/pending` وتكتب أحداثًا وسجل تدقيق داخل transaction.

**السبب:** قد يطلب المستلم الإيقاف بعد قبول الرسالة وقبل موعد تنفيذها. فحص route وحده غير كافٍ.

**النتيجة:** opt-out محلي لكل مؤسسة لأن الموافقة تخص العلاقة بين المستلم والمرسل. إذا سبق الإيقاف، يراه العامل ويلغي الرسالة؛ وإذا سبق اتصال العامل، ينتظر تسجيل الإيقاف انتهاء الاتصال ثم يمنع الرسائل اللاحقة. يحتفظ النظام بهذه السجلات أطول من محتوى الرسائل. إذا أصبحت الرسالة `sent` فلا يدعي النظام إمكانية إلغائها من شبكة الهاتف.

## ADR-012: Webhooks موقعة وقابلة لإعادة المحاولة بأمان

**القرار:** ينشئ النظام delivery record لكل event/endpoint ويوقع `timestamp + "." + rawBody` بـHMAC-SHA256. يستخدم طابورًا مستقلًا مع exponential backoff ومعرّف event ثابت.

**السبب:** التوقيع يحمي سلامة المصدر، وسجل delivery يمنع فقد الحدث ويتيح retry دون إنشاء حدث منطقي جديد.

**النتيجة:** على المستقبل التحقق من raw bytes، timestamp، والتكرار. يفرض النظام HTTPS خارج الاختبارات المعزولة، ويمنع redirects والعناوين غير القابلة للتوجيه العام بما فيها IPv4 المضمّن وNAT64 و6to4، ويتحقق من كل نتائج DNS ثم يثبّت الاتصال على عنوان IP المفحوص لمنع DNS rebinding. مهلة الطلب حد إجمالي وليست مهلة خمول، وحجم الاستجابة محدود. لا تسجل أجسام webhook الحساسة.

## ADR-013: تصميم الحملات المستقبلية فوق مسار الرسالة نفسه

**القرار:** لا يوجد bulk bypass. أي حملة مستقبلية توسع القائمة إلى رسالة مستقلة لكل مستلم، ثم تمر عبر نفس idempotency والحصة والمعدل وopt-out والعامل.

**السبب:** مسار منفصل للحملات قد يتجاوز ضوابط الأمان أو ينتج سلوكًا مختلفًا يصعب تدقيقه.

**النتيجة:** يمكن إضافة planner وساعات عمل وفاصل أجهزة لاحقًا دون تغيير adapter أو عقد الرسالة. تبقى الرسائل التسويقية غير المصرح بها ممنوعة مهما كان مصدر الطلب.

## ADR-014: جهات اتصال معزولة مع upsert وحذف بيانات

**القرار:** تحفظ جهة الاتصال داخل مؤسسة واحدة برقم E.164 فريد، ضمن `max_contacts` في الخطة وتحت قفل مؤسسة ذري. `POST /v1/contacts` ينفذ upsert حسب `(organization_id, phone_e164)`، والقائمة تستخدم cursor مركبًا من `(created_at, id)`، والحذف يزيل صف بيانات المستلم ويبقي واقعة `contact.deleted` المنقحة في سجل التدقيق.

**السبب:** الاستيراد وإعادة مزامنة CRM ينتجان طلبات مكررة طبيعيًا؛ upsert يمنع النسخ تحت التزامن. cursor pagination أكثر ثباتًا من offset. حذف الصف يمنع تراكم tombstones وبيانات المستلمين عبر دورات الحذف/إعادة الإنشاء، بينما يبقى أثر العملية قابلًا للتدقيق بلا PII.

**النتيجة:** الاسم وtags وmetadata ومرجع الموافقة معلومات مساعدة، وليست تفويضًا دائمًا للإرسال. يظل `consent_confirmed` مطلوبًا في طلب الرسالة ويظل opt-out حاكمًا. كل قراءة وحذف مقيدان بـ`organization_id`، وتكتب عمليات الإنشاء والتحديث والحذف audit logs.

## ADR-015: تنظيف محتوى الرسائل بالتنقيح لا حذف السجل

**القرار:** ينقّح worker الرسائل النهائية بعد `retention_days` الخاصة بالخطة، على batches قصيرة باستخدام `FOR UPDATE SKIP LOCKED`. تزال أرقام المستلمين/المرسلين والمحتوى وmetadata ومراجع المزوّد والعميل والموافقة، وتُنقّح payloads الأحداث والـwebhooks وأجسام ردودها؛ تبقى هوية السجل والحالة والتوقيت وحقائق الأحداث المنقّحة والتدقيق والعدادات.

**السبب:** حذف الرسالة كاملة يضعف المصالحة والفوترة والتدقيق، والاحتفاظ بالنص بلا نهاية يزيد أثر أي تسريب. التنقيح يفصل الحاجة التشغيلية طويلة الأجل عن البيانات الشخصية قصيرة الأجل.

**النتيجة:** يبدأ العمر من `created_at` حتى لا تؤجل تحديثات الحالة التنظيف. sweeper مستقل ينقل `queued` المنتهية و`sent` التي انتهت نافذة إيصالها إلى حالة نهائية أولًا. لا تُحذف opt-outs. الفهرس الجزئي يقتصر على الحالات النهائية غير المنقحة، ويمكن لعدة workers تقاسم العمل بأمان.

## ADR-016: خطة مجانية دائمة بحدود استخدام صريحة

**القرار:** توجد خطة `free` دائمة بلا رسوم منصة وبحصة 1000 عملية رسالة شهريًا و10 عمليات في الدقيقة وجهاز واحد و3 مفاتيح API وWebhook اثنين و500 جهة اتصال واحتفاظ 30 يومًا. تنشئ أداة التطوير اشتراكًا `active` ومفتاح اختبار بلا انتهاء، وتدوّر المفتاح دون تصفير استخدام الشهر نفسه.

**السبب:** المطلوب جعل استخدام المنصة مجانيًا مع إبقاء تكلفة الهاتف والشريحة ورسوم شركة الاتصالات خارج المنصة، ومنع تحويل المجانية إلى وعد برسائل غير محدودة أو مسار لإساءة الاستخدام.

**النتيجة:** تتجدد الحصة مع كل شهر ميلادي وتطبقها نفس transaction المستخدمة لكل الخطط، وتظهر في `GET /v1/usage`. الحدود الشهرية وحدود المعدل والأجهزة وجهات الاتصال وWebhooks تبقى جزءًا من مكافحة الإساءة. تكاليف وقواعد الشريحة وشركة الاتصالات مستقلة، وDocker Compose يبقي المزود `mock` والإرسال الحقيقي معطلًا.

## ADR-017: ربط وضع التنفيذ بالاعتماد والرسالة من الخادم

**القرار:** يحمل كل Device credential وضعًا ثابتًا `simulation` أو `live`، وتحمل كل رسالة `execution_mode` غير قابل للتبديل بعد القبول. يجب أن يطابق تصريح الهاتف `simulated` وضع الاعتماد، لكن لا يستخدم هذا الحقل لاتخاذ قرار التنفيذ. يفحص Android claim/begin/event والـworker تطابق وضع الرسالة مع وضع المنفذ.

**السبب:** الثقة بحقل يرسله الهاتف تسمح لاعتماد Simulation بالإبلاغ كأنه حي. كما أن رسالة اختبار مجدولة قد تبقى في قاعدة البيانات ثم تُنفذ بعد تحويل الخادم إلى وضع حي.

**النتيجة:** ترحيل البيانات القديمة يربطها بأكثر قيمة تحفظًا وهي `simulation`. provisioning الافتراضي ينشئ اعتماد Simulation؛ الاعتماد الحي يحتاج إنتاجًا مع أعلام الإرسال الحي وتأكيد CLI ثانٍ حرفي. تظهر `execution_mode` في API وWebhook. أي فشل حي بعد بدء `SmsManager` أو restart يجعل النتيجة `provider_outcome_unknown` و`manual_review` بلا إعادة تلقائية.

## الفهارس والقيود الحرجة

- unique `(organization_id, idempotency_key)` على الرسائل.
- index `(organization_id, created_at DESC)` و`(organization_id, status, created_at DESC)` للرسائل.
- فهارس جزئية للرسائل الجاهزة حسب الموعد، ولـdispatch العالق، ولمصالحة حالات `sent`.
- unique active `(organization_id, phone_e164)` على opt-outs.
- unique active `(organization_id, phone_e164)` وفهرس cursor على جهات الاتصال.
- فهرس جزئي `(organization_id, created_at, id)` للرسائل النهائية التي لم تُنقح بعد.
- unique active subscription لكل مؤسسة، مع `CHECK current_period_end > current_period_start`.
- unique `key_prefix` وفهرس `(organization_id, revoked_at, expires_at)` على مفاتيح API.
- unique `(device_id, provider_message_id)` عندما يوجد معرّف مزود.
- unique `(webhook_id, event_id)` على deliveries.
- فهارس audit وevents تبدأ بـ`organization_id` وتنتهي بالوقت لتناسب الاستعلامات المعزولة.

تستخدم `timestamptz` لكل الأوقات وE.164 كنص مع validation في التطبيق وقيد قاعدة بيانات بسيط. الحذف التشغيلي soft delete أو status change؛ الحذف الفيزيائي للمؤسسة عملية إدارية منفصلة تراعي retention ونسخ الاحتياط.
