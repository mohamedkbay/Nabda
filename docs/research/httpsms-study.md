# What Nabda can learn from httpSMS

Reviewed **2026-11-08**, against upstream commit [`64244408c233a2fa52d9b5c24e52922127436c05`](https://github.com/NdoleStudio/httpsms/tree/64244408c233a2fa52d9b5c24e52922127436c05). This is a source review, not a penetration test, carrier benchmark or claim about every deployed httpSMS instance.

The user requested the Ghidra workflow. Its skill applies to compiled binaries; the supplied target is a source repository. Reading the original Go/Kotlin implementation gives better evidence here than decompilation. **Ghidra was not run, no APK was downloaded, and no upstream executable, build, test or SMS flow was executed.** A shallow reference checkout was retained under ignored `work/httpsms-reference`; it was not modified. No upstream implementation was copied into Nabda.

## Recommendation

Learn from httpSMS's notification adapters, background result uploads, diagnostic events and integration emulator. Keep Nabda's phone-owned SQLite queue, approved durable handoff, separate application/device credentials, all-part outcomes and explicit `outcome_unknown` state. Its architecture should inform the next improvements rather than replace Nabda's already prepared free hosting path.

## Details that should not be copied blindly

**Request correlation is not idempotent acceptance.** The inspected `MessageSend` request exposes `request_id`, but the send service generates a fresh message UUID and the message entity does not declare `request_id` unique. In the reviewed acceptance path I did not find a payload-bound idempotency mechanism equivalent to Nabda's `Idempotency-Key`. This is a scoped code observation, not a claim that every httpSMS endpoint lacks deduplication. Keep Nabda's workspace/key/payload conflict check and database uniqueness. [request](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/api/pkg/requests/message_send_request.go#L14), [message entity](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/api/pkg/entities/message.go#L86), [send service](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/api/pkg/services/message_service.go#L462).

**A final-part callback is not an aggregate of every part.** Android `handleMultipartMessage` gives intermediate segments suffixed IDs and the final segment the main message ID. `Receiver.isValid` rejects suffixed IDs; the API event handler also ignores those IDs. Thus this path reports the final segment's outcome rather than accumulating every segment. Keep Nabda's independently recorded sent/delivered results for all parts; no physical-device behavior was tested in this study. [multipart worker](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/android/app/src/main/java/com/httpsms/FirebaseMessagingService.kt#L326), [receiver validation](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/android/app/src/main/java/com/httpsms/Receiver.kt#L56), [event handler](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/api/pkg/handlers/message_handler.go#L294).

**Do not silently switch the sender SIM.** Upstream `SmsManagerService` can fall back to the default subscription, including a special modem exception path. Nabda's selected subscription and refusal to silently substitute a SIM are deliberate product guarantees. [SIM selection and fallback](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/android/app/src/main/java/com/httpsms/SmsManagerService.kt#L66).

**Webhook authentication differs from signing the body.** The reviewed webhook implementation adds a JWT Bearer token signed with HS256 when configured, with audience/expiry claims. Its token is not an HMAC over the exact JSON body. Requests have a five-second timeout and up to two attempts in this method. A future Nabda webhook should independently define raw-body signature verification, timestamp tolerance, event IDs, replay behavior, delivery attempts and failure history; do not advertise those as already implemented. [request creation](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/api/pkg/services/webhook_service.go#L202), [JWT claims](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/api/pkg/services/webhook_service.go#L328).

**Keep secrets out of URLs and diagnostics.** The upstream primary-key parser also accepts a key in request data/query parameters, and the shown authentication error path formats that key in a diagnostic. Nabda should retain its header-only Bearer credentials and avoid logging secrets or message bodies. These are source observations, not a tested exploit or statement about upstream log retention. [key parser and error path](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/api/pkg/middlewares/api_key_auth_middleware.go#L31).

**Do not adopt encryption marketing as a guarantee.** The Android implementation uses AES/CFB and derives an AES key from the configured string; it decrypts before calling Android's SMS API. This encrypts the application-to-phone payload path when enabled, not an ordinary SMS all the way to the recipient. Nabda does not currently implement this optional payload-encryption feature. Any addition needs an independently specified authenticated-encryption protocol and key lifecycle. This study does not validate upstream cryptography. [cipher implementation](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/android/app/src/main/java/com/httpsms/Encrypter.kt), [decrypt-before-send flow](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/android/app/src/main/java/com/httpsms/FirebaseMessagingService.kt#L424).

**Do not infer recipient consent from a generic gateway.** The reviewed send validator checks numbers, body, scheduling and sender registration; it is not evidence of a recipient-consent register or a STOP workflow. The targeted source search did not establish a complete upstream opt-out implementation. Keep Nabda's cloud recipient-hash check and phone blocklist, and add explicit opt-out administration before claiming a complete public opt-out feature. [send validator](https://github.com/NdoleStudio/httpsms/blob/64244408c233a2fa52d9b5c24e52922127436c05/api/pkg/validators/message_handler_validator.go#L130).

## Prioritized Nabda follow-up

These are proposed improvements, **not implemented by this study**.

| Priority | Work | Reviewable completion criterion |
| --- | --- | --- |
| First | Finish independent hosting and physical-phone sandbox verification | Actual GitHub sign-in on the owned API hostname; QR names that API; a phone persists, ACKs and reports a sandbox command; no carrier submission. The existing local tests do not prove this. |
| Next | Background result-outbox synchronization | A stored event survives app/service restart and uploads with the same event ID after connectivity returns. Retrying this upload never causes another modem call. |
| Next | Bounded scheduled expiry cleanup | Expired unreceived cloud payloads are removed even when the phone never returns. Add a tested, bounded cleanup schedule before publishing an exact deletion deadline. |
| Next | Clear sending diagnostics | Dashboard distinguishes “waiting for phone”, “phone has it”, “SIM needs attention”, “Android paused”, “expired”, “unknown outcome” and actual per-part results. ETAs are estimates based on the phone's pace and pending parts. |
| Later | Optional push notification adapter | Push only wakes synchronization; the SQLite/ACK protocol remains authoritative. Deduplicate wake-ups, retain polling fallback and do not promise immediate delivery. |
| Later | Signed webhook outbox and opt-out administration | Stable event IDs, per-destination secrets, bounded retries, replay checks and visible failure history; tenant-scoped opt-out add/remove/audit and phone enforcement. |
| Later | Explicit encrypted phone backup/export | Defined ownership, encryption, restore validation and handling of uncertain attempts. A cloud metadata record cannot restore message bodies already purged after ACK. |

Relevant Nabda implementation: [handoff/API](../../lib/nabda-api.ts), [SQLite and recovery](../../android/app/src/main/java/ly/nabda/mobile/LocalStore.java), [modem submission](../../android/app/src/main/java/ly/nabda/mobile/GatewayService.java), [result receiver](../../android/app/src/main/java/ly/nabda/mobile/SmsResultReceiver.java), [independent deployment](../DEPLOYMENT.md). These comparisons reflect the checked-out implementation, not a promise that every future release preserves it.
