First, give it
a phone.

Start with an Android phone. A spare phone works too. You can try sandbox mode before selecting a SIM or granting SMS permission; real sending needs an active SIM.

  1. Install the Android app.

    The Nabda APK runs on Android 8 or newer. This is a signed test build. SMS and phone permissions are needed for carrier sending. The pairing code can also be entered manually if you prefer not to use the camera.

  2. Pair it once.

    Sign in to the account dashboard, name the phone, and create a pairing code. Scan it in the app. The code lasts ten minutes and works once.

  3. Pick a SIM and make a key.

    Start Connect in test mode on the phone. Create an application API key in your account and keep it on your server. Select a SIM before enabling real phone sending.

Two SIMs? You choose which one sends. Nabda won't quietly switch numbers.

Now, ask for
a text.

An appointment reminder is a good first example. Your app makes one HTTP request with the device, recipient, and message.

This one is a sandbox request.
No SMS leaves the SIM.

POST /v1/messages

curl https://api.example.invalid/v1/messages \
  -H 'Authorization: Bearer YOUR_APPLICATION_KEY' \
  -H 'User-Agent: MyApp/1.0' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: appointment-204-v1' \
  -d '{
    "device_id": "YOUR_DEVICE_ID",
    "to": "RECIPIENT_IN_E164",
    "content": "Your appointment is tomorrow at 10.",
    "sandbox": true
  }'

Replace the key, device ID, and recipient before running it. Example text only.

What's in the envelope?

device_id
The paired phone that should do the work.
to
The recipient's number in international E.164 format. Libyan local numbers are also normalized by this edition.
content
The text itself. Spaces and line breaks are preserved.
sandbox: true
Run the handoff through the phone without using the carrier. Keep this on for your first test.

The phone has its own credential.
Your app key stays in your app.

If your connection retries...

Send the same payload with the same Idempotency-Key. Nabda returns the same message record. Reusing that key for a different payload returns 409. Use a fresh key for a genuinely new message.

The key must contain 8–128 visible, non-space ASCII characters. Application keys are shown once, stored as hashes, and can be revoked.

The queue lives
in the phone.

This is the important part. Android saves the message in its own SQLite database before it can send anything.

  1. The server temporarily holds the request.
  2. The phone saves it and asks the server to acknowledge the handoff.
  3. Only an approved acknowledgement releases the local job.
  4. The server clears the command's text and recipient. The phone keeps the queue and history.

After that handoff, the phone can continue received work when its internet drops. New requests and result uploads wait for the connection to return.

The computer can close. The phone needs to stay on, with its service running and SIM ready. The website isn't the SMS sender.

A new request may wait. This edition checks for work about once a minute while idle. Instant push and webhook delivery aren't configured yet.

“Accepted” is just
the beginning.

The API returns 202 Accepted when it has saved a command. That doesn't mean the phone has sent it, or that the recipient has received it.

  1. acceptedServer saved it
  2. on_devicePhone acknowledged it
  3. queuedWaiting locally
  4. processingAttempt started
  5. sentPhone reports sent
  6. deliveredAll parts reported delivered

Long messages travel in pieces.

Android divides the text into SMS parts. The phone tracks each part; one API request can cost several SMS. Your carrier sets those charges.

Sometimes the answer is “unknown”.

If the app is interrupted around a modem call, it may not know whether a part went out. It records outcome_unknown instead of blindly sending the same text again. Late callbacks can resolve that uncertainty.

Not every journey ends in delivery.

A message can also be failed, expired, or cancelled. Carrier receipts aren't always available. These are device-reported results, not proof someone read the text.

The API,
on one sheet.

Your base URL is https://api.example.invalid. Application requests use your Bearer key. Device credentials and browser sign-in are separate.

Keep the message ID.
It's how you follow the story.

RequestWhat it does
POST/v1/messagesSave a send command. Requires Idempotency-Key. Returns a message record with 202.
GET/v1/messages/{id}Read status, times, device, and SMS-part counts. The original text and recipient aren't returned.
POST/v1/messages/{id}/cancellationsCancel before the phone's approved handoff. After handoff, request cancellation from the phone.
GET/v1/usageRead accepted commands, pending handoffs, active devices, and device-reported sent messages and parts.
GET/healthCheck that the control plane is responding. It doesn't test your SIM or carrier.

A response has tracking details.

The accepted response is the message record itself, without a wrapper. id, status, device_id, sandbox, timestamps, part counts, cancellation state, and a failure code describe its progress.

{
  "id": "MESSAGE_ID",
  "status": "accepted",
  "device_id": "YOUR_DEVICE_ID",
  "sandbox": true,
  "handed_off_at": null,
  "parts_total": null,
  "parts_sent": null,
  "parts_delivered": null
}

An excerpt of the response fields; identifiers are placeholders.

Send later, or let it expire.

Add send_at as an ISO 8601 timestamp to schedule up to 30 days ahead. Optional expires_at must be after the send time and within the supported 31-day window.

Without an explicit expiry, work expires 24 hours after the later of now or its scheduled send time. A phone being offline doesn't pause that deadline.

Read usage carefully.

accepted_commands counts new commands. pending_handoffs counts work awaiting the phone. reported_sent_parts comes from device reports. carrier_cost is null; Nabda can't read your SIM bill.

The complete send request

Use Authorization: Bearer YOUR_APPLICATION_KEY, Content-Type: application/json, and a new Idempotency-Key for each new message. Identical retries reuse that key and payload.

JSON fieldRequiredMeaning
device_idYes · stringAn active paired phone in your workspace. Copy its ID from your account.
toYes · stringA valid international number, or a supported Libyan local form. Normalized before deduplication and opt-out checks.
contentYes · stringNon-empty text, up to 4,000 UTF-16 units. Whitespace and line breaks are retained.
sandboxNo · booleanSet this to true for testing. The raw API defaults to false when omitted; the supplied clients and Postman example explicitly default to true.
send_atNo · timestampAn ISO 8601 time with a timezone. Defaults to now. Schedule up to 30 days ahead; the phone owns the local schedule after handoff.
expires_atNo · timestampLater than now and the send time, within 31 days. Defaults to 24 hours after the later of now or send_at.

Text length and platform allowance are separate from SMS-part count, carrier capacity, and your SIM bill. The whole JSON body must fit within 128 KiB.

What the response fields mean

id and device_id
The message identifier and its assigned phone.
created_at, updated_at
Server timestamps, with the schedule in send_at and expiry in expires_at.
handed_off_at
Null until the server approves the phone's durable acknowledgement.
parts_total, parts_sent, parts_delivered
Initially null. Counters become known when the phone reports them. A missing count does not mean zero SMS were sent.
cancellation_requested
Whether cancellation was requested. Check the result rather than assuming it stopped the modem.
failure_code
A symbolic reason if supplied by the phone or server; otherwise null.

Reads and cancellation are scoped to your workspace. Cancellation before approved handoff returns guaranteed: true. After handoff it returns guaranteed: false until the phone confirms cancellation. Repeating a request for an already cancelled message keeps it cancelled.

Usage includes day_utc, accepted commands, pending handoffs, active devices, reported sent messages and parts, and the applicable limits. The source is device_reported.

The dashboard uses GitHub sign-in and a private Nabda session on the API server. An application key cannot create keys or pair devices, and a device token cannot use application routes. Never try to authenticate by setting identity headers yourself.

The phone protocol, step by step.

  1. POST /v1/device/pair: send the one-time pairing token and device details. Store the returned phone credential securely.
  2. POST /v1/device/poll: report readiness and fetch up to 25 commands. A repeated command still has the same ID.
  3. Commit the command to SQLite before POST /v1/device/ack. Only returned acknowledged IDs may execute; handle every rejected reason.
  4. POST /v1/device/events: upload stable event IDs, message ID, status and timestamp, with consistent part counts. Reusing an event ID for changed data returns 409.

The supplied Android app implements this protocol. Polling, ACK and events use the device Bearer token; pairing uses its one-time token. App keys are a different credential. A sandbox report verifies the software path, not carrier delivery.

Under the hood: the phone's four requests.

POST /v1/device/pair consumes a pairing token. POST /v1/device/poll fetches up to 25 pending commands. POST /v1/device/ack approves durable handoff. POST /v1/device/events uploads deduplicated results, up to 100 events at a time.

Ordinary applications don't use these device endpoints. For every field, management route, and error schema, the OpenAPI specification is available as a plain JSON file.

When the API says no

400 malformed JSON · 401 invalid or revoked credentials · 404 unavailable resource · 409 conflicting idempotency, state, or opt-out · 413 body too large · 415 wrong content type · 422 invalid fields · 429 workspace allowance reached.

Read the JSON error's code and message. Resolve the cause rather than repeatedly creating new message requests.

A few things
you'll probably ask.

Can I test it without sending an SMS?
Yes. Start the phone in test mode and send sandbox: true. It exercises the handoff and local queue. It doesn't prove carrier delivery. When you're ready for a real test on a number you control, explicitly start phone sending in the Android app.
Can I turn the computer off?
Yes, after the phone has received and acknowledged the work. Keep the phone on and its service running. It still needs internet for new requests and for uploading results.
What if I stop it?
Local stop prevents new modem submissions. Cancellation from the website needs to reach the phone. An SMS already submitted to the modem can't be recalled. Revoking an offline device doesn't instantly erase the queue it already owns.
Why hasn't a new request arrived?
Idle polling is about once a minute. Also check the service, connection, SIM, permissions, test/live mode, schedule, and expiry. The phone's local history has the detailed record.
Python gives me Cloudflare error 1010.
Some default library user agents are rejected before reaching the API. Set a descriptive User-Agent, such as MyApp/1.0. It identifies your client and doesn't replace the API key. This is Cloudflare's documented client setup.
Is this a finished production gateway?
This is the first working edition. The APK is debug-signed for testing. Physical-device permissions, background endurance, SIM behavior, and carrier delivery still need controlled tests. Push, public webhooks, contacts sync, and phone backup aren't included.

Your data,
plainly explained.

The phone keeps text, recipients, attempts, part outcomes, and full local history. The cloud keeps account identity, hashed credentials, device records, temporary commands, and status metadata.

Command content is cleared after approved handoff. Unreceived expired work is cleaned when the phone polls, or through cancellation or revocation; there isn't a scheduled retention job with a guaranteed deletion deadline. Phone backup and restore aren't included. Losing local app data can mean losing history.

GitHub verifies your sign-in. Cloudflare hosts the API and account records; Netlify serves this illustrated guide. The illustrated guide does not fetch your account or submit messages. The hosting platform may add its own browser security checks.

Send something
people expect.

An appointment reminder. An order ready for pickup. An update someone asked to receive. Use Nabda for legitimate messages and respect requests to stop. The cloud checks its opt-out list and the phone checks its local blocklist.

Fraud, impersonation, harassment, and unsolicited bulk messages aren't acceptable uses. You manage your phone, carrier agreement, permissions, and SMS costs. A free API isn't a guarantee that a phone is online or a message will arrive.

Don't rely on this edition alone for emergency communication. The project is made for learning, building, and maintaining something useful.
